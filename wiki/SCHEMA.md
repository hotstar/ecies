# Wiki Schema

This file is the **authoritative contract** for every page under `wiki/`. All `llm-wiki`
agents read it first and must follow it exactly; where an agent prompt and this file disagree,
**this file wins**. `initialize-wiki-agent` copies this template into `wiki/SCHEMA.md` verbatim —
edit the copy in `wiki/` to tune the contract for your repo.

## Frontmatter

Every content page begins with a YAML frontmatter block delimited by `---`. **All five fields are
required and must appear in this order:**

| Field | Required | Format | Notes |
| --- | --- | --- | --- |
| `title` | yes | Plain string | Human-readable page title. Sentence/Title case; no Markdown. |
| `last_reviewed` | yes | `YYYY-MM-DD` (UTC) | Set to the date the page was created or last **materially** changed. See [Freshness](#freshness). |
| `tags` | yes | YAML list of strings | Lowercase, kebab-case keywords for search and grouping. |
| `folder` | yes | Subdirectory name | Must equal the `wiki/` subdirectory the page lives in. Drives routing and the index. |
| `sources` | yes | YAML list of strings | Provenance — where this page's content came from. Use `[]` for purely hand-authored pages. See [Provenance](#provenance). |

`folder` must be one of the taxonomy subdirectories below.

Example:

```yaml
---
title: Playback Session Lifecycle
last_reviewed: 2026-06-02
tags: [playback, sessions, drm, lifecycle]
folder: architecture
sources:
  - code:src/session/lifecycle.ts
  - confluence:123456
agent_routing:
  code_change_relevance: conditional
  task_intents: [api-contract-change]
  applies_to_paths:
    - src/session/**
  applies_to_symbols: [SessionService]
---
```

### Optional `agent_routing`

Content pages may include optional routing hints for `wiki-integrator-agent`:

```yaml
agent_routing:
  code_change_relevance: conditional
  task_intents: [api-contract-change]
  applies_to_paths:
    - src/api/**
  applies_to_symbols: []
```

- `code_change_relevance` may be `required`, `conditional`, or `skip`.
- `task_intents` are kebab-case route intents such as `repo-onboarding`,
  `api-contract-change`, or `operations-change`.
- `applies_to_paths` are repo-relative globs that make the page relevant.
- `applies_to_symbols` are optional function, class, endpoint, module, or config names.

Use `agent_routing` only when a page should influence future task routing. Low-level implementation
pages should omit it or set `code_change_relevance: skip`.

## Folder taxonomy

| Folder | Purpose |
| --- | --- |
| `overview/` | High-level product, team, and repo introductions. |
| `architecture/` | System diagrams, service boundaries, component descriptions. |
| `api/` | Public and internal API surfaces, contracts, examples. |
| `data/` | Schemas, data flows, storage layers, retention rules. |
| `domains/` | Business-domain concepts and glossary entries. |
| `engineering/` | Build, test, deploy, local dev, and contribution guides. |
| `decisions/` | ADRs and significant technical decisions. |
| `operations/` | Runbooks, oncall guides, SLOs, incident playbooks. |

## Agent routing layer

`wiki/context-router.json` is generated by `wiki-integrator-agent`. It is a compact,
machine-readable routing file that agents read before deciding whether to open wiki pages at all.
It should stay intentionally small: the wiki is optional context, not a mandatory pre-read.

Agents should inspect `wiki/context-router.json` first. If no route matches the task, especially
for localized code changes, stack traces, exact file/function requests, cosmetic edits, and
test-only fixes, agents should skip wiki pages and go directly to code.

The router uses this shape:

```json
{
  "version": 1,
  "default_for_code_changes": "skip_wiki",
  "generated_from": ["wiki/index.md", "wiki/map.md", "wiki pages"],
  "routes": [
    {
      "name": "api-contract-change",
      "intent": "api-contract-change",
      "confidence": "high",
      "coverage": "strong",
      "match": {
        "keywords": ["endpoint", "request", "response", "contract"],
        "paths": ["src/api/**"],
        "symbols": []
      },
      "read": ["api/session-service.md"],
      "reason": "API contract changes should honor documented boundaries and decisions."
    }
  ]
}
```

Each route requires:

- `name` — stable kebab-case route name.
- `intent` — stable kebab-case task intent.
- `confidence` — `high`, `medium`, or `low`. Generated routers should emit only `high` or
  `medium`; low-confidence routes must not cause mandatory wiki reads.
- `coverage` — `strong` or `partial`.
- `match.keywords` — task words or phrases that suggest this route.
- `match.paths` — repo-relative source globs that suggest this route.
- `match.symbols` — optional function, class, module, endpoint, or config names.
- `read` — wiki page paths relative to `wiki/`.
- `reason` — one short explanation of why this context matters.

Router rules:

- `default_for_code_changes` must be `skip_wiki`.
- Every `read` path must resolve to an existing content page under `wiki/`.
- Do not route to `index.md`, `map.md`, `log.md`, `SCHEMA.md`, `.llm-wiki-state.json`, or
  `context-router.json`.
- Prefer a few high-confidence routes over exhaustive routing.
- Do not create routes for low-level code details, individual helper functions, single files, or
  implementation walkthroughs that are faster and safer to inspect from source.
- Partial routes should tell agents to skim the routed page and verify in code immediately.

## Documentation scope (the `code-doc-config` gate)

`wiki/code-doc-config.yaml` is the single allowlist for **which subjects the wiki is allowed to
document**. Its `document.*` toggles are code-derivable categories, and each category maps to one
folder above (see the category→folder table in `code-ingestion-agent`). Collapsing that map by
folder gives the **documentation-enabled folders**: a folder is *enabled* when at least one
`document.*` key that maps to it is `true`.

| Folder | Governing `document.*` keys | Gated? |
| --- | --- | --- |
| `overview/` | `overview` | enabled when any is `true` |
| `architecture/` | `module_structure`, `architecture`, `dependencies`, `entry_points`, `error_handling` | enabled when any is `true` |
| `api/` | `public_api`, `internal_api` | enabled when any is `true` |
| `data/` | `data_models`, `data_flow` | enabled when any is `true` |
| `domains/` | `domain_concepts` | enabled when any is `true` |
| `engineering/` | `configuration`, `build_test_deploy`, `conventions` | enabled when any is `true` |
| `operations/` | `operations` | enabled when any is `true` |
| `decisions/` | — (no `document.*` key) | **always enabled** — never gated |

This gate applies to **every** agent that writes a content page, regardless of where the content
came from — the live code or an explicitly linked external source (Confluence, Google Docs/Sheets,
GitHub PRs, git commits):

- A page may only be created or updated in an **enabled** folder.
- A folder with no governing key (`decisions/`) is always enabled and is never gated.
- When content would route **only** to a **disabled** folder, the agent must **not** write it: it
  skips that content and reports it as gated (e.g. `skipped: api/ disabled in code-doc-config`). A
  source that also has content for an enabled folder is still written there.
- `code-ingestion-agent` additionally gates at the finer **per-category** level (it never writes a
  page for a `false` category, even within an enabled folder). Every other agent gates at the
  folder level defined here.
- If `wiki/code-doc-config.yaml` does **not** exist, nothing is gated.

This gate is independent of `scan.include` / `scan.exclude`, which bound only the **code** that
`code-ingestion-agent` reads — they do not apply to external prose.

## Provenance

The `sources` field lets `/refresh`, `/update-doc`, and the writing agents target page updates to
the origins that actually changed. It is page provenance, not the discovery mechanism for tracked
external refreshes: `/refresh` discovers Confluence / Google Docs / Google Sheets sources only from
`wiki/.llm-wiki-state.json.external_sources`. Each entry records one origin, using a prefix:

- `repo-doc:<repo-relative-path>` — repository documentation outside `wiki/` that contributed content.
- `code:<repo-relative-path>` — a source file, manifest, script, workflow, or config file the page was derived from.
- `confluence:<pageId>`, `gdoc:<docId>`, `gsheet:<spreadsheetId>`, `github-pr:<number>`, `git-commit:<sha>` — an external source.
- A bare absolute URL for anything else.

Append new origins when a page absorbs additional material; never drop an origin that still
contributes content. Hand-authored pages with no upstream use `[]`.

## Codebase scan state

`wiki/.llm-wiki-state.json` is committed agent-owned metadata used by `/refresh` to avoid
reprocessing unchanged source files, to revisit tracked external MCP documents, and by
`/update-doc` to avoid refetching unchanged external MCP documents. It records the latest
successful codebase scan timestamp, the latest full-scan timestamp, the hash of
`wiki/code-doc-config.yaml`, the SHA-256 content hash of each in-scope source file, and revision
metadata for external Confluence / Google Docs / Google Sheets sources.

The timestamp (`last_codebase_scan_at`) is for auditability. File content hashes are the source of
truth for delta detection, because filesystem modified times are not stable across machines, clones,
rebases, or checkouts.

The state schema version is currently `2`. Version 2 keeps the code scan fields from version 1 and
adds an `external_sources` object keyed by normalized source id:

- `confluence:<pageId>`
- `gdoc:<docId>`
- `gsheet:<spreadsheetId>`

Each `external_sources` entry stores metadata only, never document body content:

- `source_type`, `identifier`, `url`, `title`
- `revision_kind` and `revision_value`
- `last_checked_at` and `last_processed_at`
- `status`: `ingested`, `no_material_change`, or `gated`
- `scan_config_hash` for the `code-doc-config.yaml` hash used when the source was processed or
  gated
- `pages`: wiki page paths created or updated from that source, when known

If the state file is missing, invalid, or still uses version 1, commands must preserve existing code
scan behavior and treat the external source state as empty until a successful external-source run
or code scan writes version 2. `/refresh` discovers tracked external sources **only** from
`external_sources`; it must not recover them from page frontmatter, raw URLs, or old Confluence
space arguments. State tracks individual Confluence pages, Google Docs, and Google Sheets, so
`/refresh` revisits only those recorded ids and does not enumerate new pages in a previously used
Confluence space. If the state file was produced with a different
`code-doc-config.yaml` hash, `/refresh` must fall back to a full codebase scan and recreate the
code scan fields while preserving valid `external_sources` entries unless the user is doing a clean
bootstrap rebuild.

For external MCP documents, `/bootstrap`, `/update-doc`, and `/refresh` compare provider revision
metadata against `external_sources` before fetching full body content. Prefer Confluence page
version for Confluence, Drive revision/version for Google Docs/Sheets, and Drive `modifiedTime`
only when no better revision is exposed. If the provider revision differs from the stored
`revision_kind` or `revision_value`, fetch and normalize the body content; if it matches, skip the
body fetch. During `/refresh`, a successful unchanged metadata check updates only `last_checked_at`
and preserves `last_processed_at`, `status`, `scan_config_hash`, `pages`, and all revision fields.
`/refresh --full` forces a full code scan but does not force unchanged external documents to be
fetched. If cheap revision metadata is unavailable, ask the user whether to fetch the full document
body or skip that source. A source previously recorded with `status: gated` must be reprocessed
when the current `code-doc-config.yaml` hash differs from the entry's `scan_config_hash`, even if
the provider revision did not change. If an external source cannot be checked or fetched during
`/refresh`, report it and continue with the code refresh and remaining external sources.

## Linking

- **Internal links** between `wiki/` pages are **relative** to the linking page
  (e.g. `../api/session-service.md`) — never absolute filesystem paths or site URLs.
- **External links** are **absolute** URLs (`https://…`).
- Only link pages that actually exist on disk.

## Body conventions

- Headings start at `#` for the page title, then `##` for sections. Cap heading nesting at depth 3.
- **Ground every claim in a source.** Do not invent facts. If a source is thin or ambiguous, say so
  inline rather than guessing.
- A single subject lives on **one** canonical page; split multi-topic material across pages and
  cross-link rather than duplicating.

## Conflicts

When sources disagree, or code contradicts the docs, do **not** silently pick a winner. Record the
discrepancy under a `## Conflicts` section (exact heading, capital C) at the end of the page:

```markdown
## Conflicts

- `session-design-v2.md` states the heartbeat interval is 30s, but `ops-notes-2026Q1.txt`
  records 15s in production. **Needs human resolution.**
```

Omit the section entirely when there is nothing to flag. The integrator preserves these sections
and never resolves them itself.

## Freshness

- `last_reviewed` is set by the agent that **creates or materially changes** a page — never bumped
  for cosmetic/normalization-only edits.
- Pages should be reviewed by a human at least every **180 days**.
- The integrator **flags** pages past the freshness window as *needs human review* in its run
  report. It does **not** silently re-stamp `last_reviewed`, because the date asserts a real review.

## Cross-cutting files (agent-owned, do not hand-edit)

| File | Owner | Purpose |
| --- | --- | --- |
| `index.md` | `wiki-integrator-agent` | Catalog of all pages: `Page \| Folder \| Last Reviewed \| Summary`. |
| `map.md` | `wiki-integrator-agent` | Task-oriented navigation by reader intent. |
| `context-router.json` | `wiki-integrator-agent` | Compact routing metadata agents read before deciding whether to open wiki pages. |
| `log.md` | every agent (prepend) | Append-only run log. Newest entries at the **top**. Format: `YYYY-MM-DD HH:MM \| agent \| action \| notes`. |
| `.llm-wiki-state.json` | `code-ingestion-agent` and `external-update-agent` | Committed scan metadata for incremental `/refresh` and tracked external-source checks: code scan timestamps, config hash, in-scope source file hashes, and Confluence / Google Docs / Google Sheets revision metadata including `last_checked_at`. |

`index.md`, `map.md`, and `context-router.json` are regenerated by `wiki-integrator-agent` from the
pages on disk; do not edit them by hand.

**Invariant — every run that creates or updates a content page must:**

1. **Prepend a `log.md` entry** (newest at the top) describing the run. The agent that wrote the
   page does this itself, before returning.
2. **Be followed by `wiki-integrator-agent`**, which re-checks `index.md`, `map.md`, and
   `context-router.json` against the pages now on disk and rebuilds them if anything changed (a page
   added, removed, renamed, or whose title/summary/folder/freshness/routing shifted). The
   `/bootstrap`, `/refresh`, and `/update-doc` flows all run the integrator as their final step; if
   a writing agent is invoked standalone, it must tell the caller to run `wiki-integrator-agent`
   afterward.

A content page never appears in the wiki without a corresponding `log.md` entry and an `index.md` /
`map.md` / `context-router.json` that account for it.
